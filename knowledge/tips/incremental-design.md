# Incremental Design Tips

## 目的

要件を段階的に実現しながら、各変更後も関連領域の設計を一貫した状態に保つ。

## 変更時の判断

1. 変更対象だけでなく、関連する責務、利用箇所、重複、テスト、文書を確認する。
2. 現行構造で要件を自然に表現できるか判断する。不自然な分岐、責務違いの配置、同じ修正の複数コピーが必要なら、構造も改める。
3. 変更後に全体として理解しやすく、次の変更を加えやすい形を選ぶ。差分量だけで判断しない。
4. 構造変更を伴う場合は、目的、影響範囲、守るべき既存挙動、検証方法を FileChangePlan に記す。
5. 挙動を固定するテストや確認手順を用意し、段階ごとに検証する。

## Task の範囲

- 要件を一貫して満たすために必要なリファクタリングは、同じ Task に含めてよい。大規模な改修も必要性が説明できれば許容する。
- 独立して検証・受入できる変更は分割してよい。分割によって歪んだ中間状態を残さない。
- 明示された Task の完了条件や Project Policy を超える場合は、manager に範囲の調整を提案する。
- 今回の要件と関係しない設計上の問題は、根拠と影響を技術的 follow-up として記録し、現在の変更へ無断で混ぜない。

## 避けること

- 差分を小さくするために、重複や責務の不整合を増やす。
- 必要な構造変更を一律に別 Task へ先送りする。
- 美しさや将来の可能性だけを理由に、要件と無関係な大規模改修を行う。
- 既存挙動の確認なしに広範囲の構造を変える。
