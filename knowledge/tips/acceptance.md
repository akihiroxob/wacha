# Acceptance Tips

## 目的

manager の最終受入を、Task の完了確認だけでなく、要求とシステム全体の整合性を保証する判断として行う。

## Reviewer と Manager の違い

- reviewer は、実装が Task の完了条件、既存構成、設計原則、検証基準を満たすか確認する。
- manager は、成果が人と合意した要求と親 Story の目的を満たし、Project 全体へ取り込んでよいか最終判断する。

Reviewer の承認は重要な証拠だが、Manager の判断を代替しない。

## 受入で照合するもの

次を相互に照合する。

1. 人と確認した要求・制約
2. 親 Story の目的・完了条件
3. Task の完了条件
4. Project の `AGENTS.md` と主要設計資料
5. worker / reviewer のコメントと検証結果
6. 実際の差分、成果物、外部から観測できる振る舞い

資料間で矛盾し正しい期待を決められない場合は、推測で Accept しない。下記の停止原因を分類し、計画修正・中断・人への確認と、製品不具合によるRejectを区別する。

## 二層で判定する

### 1. Task の充足

- Given / When / Then / And をすべて満たしているか。
- 実装済み、未接続、未検証、fixture・mockによる模擬成功を区別しているか。
- 検証が型チェックやbuild成功だけでなく、変更した振る舞いを確認しているか。
- 要件の一部を後続対応として残したまま完了扱いにしていないか。

### 2. システム全体の整合性

変更によって追加・変更された概念を列挙し、Project の正本資料と照合する。

- Role、Principal、Human、外部サービスなどの操作主体
- Entity、状態、状態遷移、データの所有者
- API、MCP tool、CLI、Web UIなどの公開経路
- component、module、repository、実行基盤の責務境界
- 認証、認可、Credential、Projectとの紐づけ
- 冪等性、再送、timeout、retry、resume、監査・来歴

固定のアーキテクチャを前提にしない。各Projectの`AGENTS.md`と設計資料に書かれた名称・責務・境界を基準にする。

## UIの受入検証

UIに関する完了条件は、manager が実ブラウザを操作し、独立に確認する。実行環境に対応する検証Skillが提供されている場合は、接続、検証環境の準備、ブラウザ操作、終了処理をその手順に従って行う。

- 検証対象が受入対象の成果物と一致することを確認する。Gitで管理されている場合は対象のcommit SHAを記録し、GitHub連携では受入対象のマージ済みSHAと照合する。
- 利用した環境とデータを記録する。fixture・mockによる検証では、その範囲と実環境との差を明示する。
- 完了条件から確認項目を導く。必要な正常系、異常系、権限、画面幅、キーボード操作などを、対象の要件に応じて確認する。
- 操作後の画面と状態を観測する。見た目に関する条件はスクリーンショットを実際に見て判断し、DOM、API応答、型チェック、buildなどの結果と合わせて根拠を示す。
- 完了条件ごとに、操作、期待した結果、観測した結果、証拠の参照先を記録する。worker / reviewer の報告は、manager 自身の確認と照合する。

ブラウザ検証のためにE2Eテストの新規作成を必須とはしない。既存の自動テストは証拠として利用し、受入判断に必要な画面・操作を確認する。

環境制約で確認できない場合は、未検証の条件、制約、再検証に必要な条件を記録し、必須条件が未検証のままAcceptしない。環境制約だけから成果物の不具合と断定せず、実行方式が定める中断・保留手順に従う。直接Claimを取得した実行で判定を中断する場合は、理由を添えてClaimを解放する。

## 受入順と候補の選択

- ACのGivenを作る機能と、その機能を所有する先行Taskを特定する。Story / Taskの番号や優先順位だけで成立を判断せず、現在の実装・受入状態を照合する。
- 前提TaskがRejectされていれば、その不具合は前提Taskで修正・再受入する。依存するTaskを同じ不具合で重複してRejectせず、必要なTask ID・到達状態を記録して保留する。
- 直接MCPで選択するManagerは、依存が成立した別候補の受入を続ける。RunnerからTask / Claimを渡された実行は、独断で別TaskをClaimせず、依存待ちと再選択条件を実行契約に従って返す。Skillの更新だけでRunnerの候補選択・停止処理が変わるとは扱わない。
- 状態を作る製品機能が計画に存在しなければ、Storyの不足・分割を見直す。必要な機能を計画してから順序を決め、データ準備を最初の解決策にしない。
- 後続Taskの受入は、先行Taskの固定merge SHAに後続APIを追加しない。既存Taskは、その対象revisionでの検証可能性と統合検証Taskの受入境界を別途確認する。

## 検証データの準備

まず先行Taskの修正・受入、Story / Taskの順序とACの所有を確認する。依存が成立すれば通常操作で準備できる状態は、その成立を待って検証する。先行機能を待っても通常操作では作れない表示・参照の状態には、Projectで実行を許可した手順に従い、専用の検証環境へデータを直接準備してよい。データ準備後は対象の実APIから読み、実ブラウザで表示・遷移を確認する。準備時に内部Applicationを使うことやデータを直接保存することは、その操作の公開入口・保存・認可を検証した証拠にはしない。

- Projectの準備手順・シナリオ・実行許可設定を確認する。具体的なコマンド、DB構造、接続先はProjectの正本に従う。
- 専用環境・データだけを対象にし、既存の開発・運用データへ適用しない。対象コード・SHAを変更せず、準備失敗時は原因を記録する。
- 準備方法、シナリオ、作成したEntityの参照、Role・Membership、対象SHA、ログ、準備で代替した範囲と未検証範囲を記録する。認証情報を証跡へ含めない。
- 管理操作・保存・認可がACの対象なら、その公開操作を実行して確認する。応答の差し替えを実APIとの接続・保存・認可の成功と扱わない。
- 準備できない原因が本来必要な先行機能の未実装なら、Storyの順序・依存・ACの所有を確認する。必要な製品機能の不足をデータ準備で解消した扱いにしない。

## 一時実装の扱い

次のすべてを満たす場合に限り、中間状態をAcceptできる。

- 親 Story が段階導入を許可している。
- 現在の Task の完了条件が、その中間状態を明示的に許容している。
- 恒久状態への移行条件が分かる。
- 不足を解消する Task がすでに作成され、追跡できる。

単に「後で直す予定」であることは、現在の不整合をAcceptする理由にならない。

## Accept 条件

- 現在の Task が所有する完了条件を満たし、親 Story の目的・制約と矛盾しない。Story全体の未完了の統合条件は、明示した所有 Task で検証する。Story完了時は統合条件を含む全体の充足を確認する。
- 人と確認した要求・制約に反しない。
- Project の正本資料が定義する責務境界・用語・公開経路と整合する。
- 実際の振る舞いを示す十分な証拠がある。
- 未解決の重要な疑問や、追跡不能な不足がない。

## Reject reason の書き方

最低限、次を含める。

- 期待した状態
- 確認できた実際の状態
- 差分が受入を妨げる理由
- 再受入に必要な条件

テストが成功していても、要求またはProjectの責務境界に反する場合はRejectする。

## 停止原因と計画修正

| 原因 | 行動と再開条件 |
| --- | --- |
| 製品不具合 | 実行可能なACに対する実際の不足を示してRejectし、修正と検証を求める |
| 検証環境 | 接続・権限・データなど不足を記録し、復旧後に再検証する |
| 未成立の依存 | Task ID・必要な到達状態を示し、成立後に再選択する |
| ACの割当不整合 | 要件を保持した分割・順序・検証先の変更をManagerが行い、修正後のACを再評価する |
| 人の判断待ち | 成果・制約・認可・業務規則の変更など、判断が必要な点を具体化して確認する |

分類と再開条件は判断根拠・Task本文・実行結果として残す。これは運用手順であり、サーバーの構造化された依存判定・停止分類・自動再開が実装済みであることを意味しない。

Managerが自律的に変更できるのは、合意済み要件を維持したACの重複除去・検証位置・Taskへの割当・前提の明示である。製品不具合の回避、必須条件の削除、未検証の成功扱い、ユーザーの成果・制約・認可・業務規則の変更は含めない。

ACを移す場合は、移動先が未完了であり、その対象 revision でGiven・観測方法を準備できることを確認する。移動先の本文へ条件を保存してから移動元を更新し、親Storyの受入境界・条件の前後・移動先Task ID・理由を記録する。途中で失敗したら既存の割当を保持し、未割当のまま受入しない。受入済みTaskへ義務を追加せず、必要なら追跡可能な新規Taskを作る。

過去の差し戻しコメントは削除しない。最新指示・正本資料との整合を確認した現在のTask本文を受入条件として読み、古いコメントの条件を無条件に再要求しない。独断で解消できない仕様の矛盾は人へ返す。

直接MCPを操作するManagerは `edit_story`・`edit_task`・必要なら `issue_task` で計画を修正する。RalphがTask/Claimを渡した実行では、その実行契約で許可された範囲だけを操作する。計画編集が許可されていなければ、修正案・原因・再開条件を結果に返し、停止解除や状態変更を独断で行わない。

## 証拠の再利用と再受入

- 既存のManager証拠は対象Task・commit SHA・検証内容・環境・データ・結果を照合し、ソースと検証に影響する条件が変わらず、現在のACを満たす場合に再利用する。Worker / Reviewerの承認だけで独立した受入検証を代替しない。
- UI条件の再利用でも、保存された操作結果と画像を実際に確認する。証拠が取得できない・古い・条件が異なる範囲は再検証する。
- ACの割当のみを修正した場合は、残る条件へ有効な証拠を照合し、不足だけを検証する。対象SHAを後続commitへ置き換えて先行Taskを受け入れない。
- 現在のTask・Claim・PR状態を確認し、正規のMCPまたはRunnerの実行契約で新しい判断を記録する。過去の `blocked` 結果を機械的にAcceptへ変更しない。
