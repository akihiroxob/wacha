# Task Writing Tips

## 目的

Task を、worker が着手時に迷わず、reviewer が完了判定しやすい形で書く。

## 良い Task の条件

- 何を変えるかが 1 文で分かる
- 完了判定ができる
- 範囲外が分かる
- 必要な前提が書かれている

## まず決めること

- この Task は何を終わらせるのか
- どの挙動を確認できれば完了か
- 壊してはいけない既存挙動は何か
- 不明点があるなら、実装前に誰が判断するか

## 書き方

Task の description は Gherkin を基本にする。

```md
Given 前提
When 実行すること
Then 確認したい結果
And 補足の結果や非対象
```

## 書くべき内容

- 対象: どの画面、API、ユースケース、文書か
- 結果: 何が変わるか
- 制約: 何は変えないか
- 確認観点: テストまたは手動確認で何を見るか

## そのまま着手できる Task の目安

- worker が追加質問なしで最初の一手を決められる
- reviewer が reject 条件を想像できる
- 「終わったかどうか」をコード以外の言葉で説明できる

## 書き直したほうがよい Task

### 悪い例

```md
Task をいい感じに整理する
```

何をもって完了か分からない。

### 改善例

```md
Given Project 画面で Task 一覧を表示している
When status アクセプト待ち一覧のボタンを押すと
Then `wait_accept` を含む全状態の件数が見える
And 既存の `todo` `doing` `in_review` `accepted` `rejected` 表示を壊さない
```

## 分割したほうがよい兆候

- 「調査して決める」が主文になっている
- 2 つ以上の成果物に別々の完了条件がある
- reviewer が複数の論点を別々に判断しないと通せない
- 実装と follow-up 設計が同居している

## reject されにくい書き方

- Then は観測可能な結果にする
- And で既存維持条件を書く
- 非対象を短く書く
- 曖昧語を減らす

避けたい曖昧語:

- 適切に
- 必要に応じて
- 可能なら
- いい感じに
- 柔軟に

## 最低限のテンプレート

```md
Given 対象と前提が分かっている
When 追加する操作する方法が記載されている
Then 期待する結果が確認できる
And 壊してはいけない条件が維持される
```

## ACの前提を準備できるか確認する

起票時・AC変更時・差し戻し条件の追加前に、新規または変更したACごとに次を確認し、Task本文へ実行に必要な情報を残す。

| 項目 | 確認すること |
| --- | --- |
| 所有 Task | このACを完了させる Task ID は一つか。統合条件はどの Task が担うか |
| Givenの準備 | データ・Role・状態を、どの公開操作または承認済みfixtureで作るか |
| 利用可能時点 | 準備入口が先行 Task で成立するか、同じ Task が提供するか |
| 観測 | 実ブラウザ・API・Domainテストなど、要件に必要な方法は何か |
| 対象 revision | 当該 Task の対象SHAで完結するか、別の統合検証 Task が必要か |
| 依存 | 依存 Task ID、必要な実装・受入状態、再選択条件は何か |
| 制約 | 権限・sandbox・接続先・一時データ・終了処理を準備できるか |

後続機能なしではGivenを作れない場合は、Managerが順序・分割・ACの割当を修正する。番号や `sortOrder` の変更だけで依存が解消したと扱わない。依存制御が未実装の場合、候補に表示されることは前提成立の証拠にならない。

Reviewer / Worker は要件を独断で変更せず、具体的な未成立の前提と修正案をManagerへ返す。差し戻しは現在の要件を満たす修正に限定し、新たな統合条件が必要なら所有 Task と依存をManagerが決める。DB直接操作やmockによる成功を、公開操作で準備することが要件のACの代替にしない。
