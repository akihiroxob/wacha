# Project Defaults

## 目的と適用範囲

Project に技術・構成の方針がまだないとき、人にも agent にも読みやすく、変更箇所を予測しやすい出発点を与える。この文書は新規 Project の推奨構成であり、既存 Project の移行指示ではない。

判断の順序は、明示された要求・制約、対象 Project の `AGENTS.md` と設計資料、既存コードの一貫した構成、この文書の推奨構成とする。Project の資料が一部だけを定める場合は、未指定の部分にだけ推奨構成を使う。既存コードと推奨構成が異なるだけでは構成を変更しない。変更が必要なら、現在の Task の目的・影響・検証方法に基づいて判断する。

## 推奨する技術

| 対象 | 方針がない場合の推奨 | 適用条件 |
| --- | --- | --- |
| Web、API、CLI の言語 | TypeScript。型チェックは `strict` を有効にする | 対象の実行環境が TypeScript に適している場合 |
| Web UI | React と Vite | クライアント主体の画面・アプリの場合。サーバー描画、検索流入、配信環境などに固有の要件があれば Project で選定する |
| API サーバー | Node.js と Hono | HTTP API を新規に構築する場合。既存の実行基盤や運用制約があればそれを優先する |
| UI のスタイル | SCSS と共有デザイントークン | 新しい React UI の方針が未指定の場合。詳細は `knowledge/principles/frontend-architecture.md` に従う |

Web UI、API、CLI のうち必要なものだけを採用する。他の種類のソフトウェアに TypeScript や React を当てはめない。バージョン、状態管理、ルーター、DB、ORM、テストツールは、必要な要件と既存環境を確認して選ぶ。推奨構成を満たすためだけに依存や層を追加しない。

## 推奨する配置

新しいディレクトリは、そこに置く実ファイルが必要になった時点で作る。以下は配置先を選ぶための例であり、空の雛形を一括生成する指示ではない。

```txt
src/
  app/             # Web の起動、ルーティング、画面合成
  features/        # 機能固有の UI と振る舞い
  components/      # 複数機能で使う UI
  lib/             # 機能に依存しない小さな処理
  server/          # API の起動と HTTP の入口。API がある場合のみ
  domain/          # 技術に依存しない業務ルール。分離が必要な場合のみ
  application/     # ユースケース。分離が必要な場合のみ
  infrastructure/  # DB や外部サービスとの接続。必要な場合のみ
test/              # 既存のテスト配置がなければ、対象コードを追いやすく置く
docs/              # Project 固有の設計・運用判断
AGENTS.md          # Project 固有の agent 向け方針
```

フロントエンドと API の両方がある場合でも、責務が混ざらないなら同じ `src/` でよい。規模やビルド境界が必要になれば、Project の資料で `frontend/` と `server/` などに分ける。配置は名前をそろえることより、責務と依存方向が読み取れることを優先する。

## Project で決めること

推奨と異なる選択、または推奨が決めていない重要な選択は、対象 Project の `AGENTS.md` や設計資料に理由とともに残す。Task を進める agent は、その Project の選択を正として実装・レビューする。Wacha の共通知識には、単一 Project だけに通用する技術判断を追加しない。
