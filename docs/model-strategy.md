# モデル差と品質安定化の戦略

## この文書について

2026-07 の Fable 5 とのセッションで得た分析を記録したもの。経済的に強いモデルを常用できない前提で、wacha がどうやって開発品質を安定させるかの方針をまとめる。

読者は wacha を開発・運用する人間。agent に配信する knowledge ではない（agent 向けの規範は `knowledge/` にある）。

## 前提となる経緯

wacha は AI オーケストレーションのために始まった。

1. オーケストレーションには共通認識が必要 → Story / Task 管理とコメントを追加した
2. 次に開発力が問題になった（1 ファイル 1000 行、責任範囲の越境）→ 定型作業を Skill に、Story の作り方や開発原則を Knowledge に足した
3. それでもなお「既存コードを無視する」「定数やコンポーネントを確認せずに新設する」が再発している

この 3 が本文書の出発点である。knowledge には既に「既存構成を最優先する」「新規ファイル作成を抑制する」が明文化されている（`development-principles.md` 原則 5・6、`frontend-architecture.md` の探索ルール）。**明文化済みのルールが再発しているという事実自体が、散文の追記では解決しないことの証拠**であり、対策の軸を変える必要がある。

## モデル差はどこに出るか

強いモデルと弱いモデルの差は「書かれていないことをどう扱うか」に出る。

### 1. 矛盾への気づき

強いモデルはドキュメントを「従う対象」ではなく「検証する対象」として扱う。実例: role-policy.md に「manager は claim_task 禁止」とあるのを読んだ上で「では実際に通るのか」を試し、仕様と実装の乖離を発見した（`wacha-retrospective.md` 2026-07-06 参照）。

この動きはチェックリストに書けない。書いた瞬間にチェックリストの一項目になり、リストにない矛盾は素通りする。

### 2. 高度（altitude）の選択

強いモデルは「何をやらないか」を判断できる。既存の knowledge 群を読んで「大部分は良い、穴は 2 つだけ」と手を止められる。弱い実行ほど「頼まれたから全部書き直す」「10 ファイル追加する」方向に行く。やらない判断は、やることリストでは規範化しにくい。

### 3. 自己申告の正直さ

弱いモデルは「ビルドが通った＝動作確認済み」と本気で信じて書く。嘘の意図がなく、検証の粒度の認識自体がずれている。「セルフレビューせよ」という指示を読んでも、その実行品質は読んでいるモデル自身に律速される。

**指示は同じモデルが解釈する。足場（scaffolding）は掛け算であって足し算ではない。** これが散文による対策の根本的な限界である。

## Knowledge / Skill でカバーできる範囲と限界

### できること: 床を上げる

FileChangePlan の強制、既存探索の記録義務、セルフレビュー工程の挿入は、弱いモデルの最頻出の失敗を潰すので分散が縮む。天井は上がらないが、床が上がるだけで実用性は大きく変わる。

### 限界と逆効果

- チェックリストが長くなるほど、弱いモデルは字面をなぞる儀式になる
- knowledge が増えるほどコンテキストが薄まり、1 件あたりの重みが下がる
- ルールの適用可否（このルールは今回関係あるか）の判断自体がモデル依存

### 判断基準

**同じルールが繰り返し破られたら、散文を書き直すのではなく、機械化するかレビューで捕まえる構造に変える。** 「既存を確認せず定数/コンポーネントを新設する」の再発はこの典型で、knowledge へのこれ以上の追記は解決策にならない。

再発の検出には `docs/wacha-retrospective.md` と `knowledge/CHANGELOG.md` を使う。同種の違反・同種の提案が 2 回目に出た時点で機械化候補として扱う。

## 散文より効く 2 つの構造

### 構造 1: 検証を散文から機械へ

「よく確認せよ」は解釈依存だが、「このテストが通ること」「この呼び出しは拒否される」は解釈の余地がない。**安全装置が解釈に依存しない度合いが、そのままモデル非依存の度合いになる。**

wacha 本体でやれること（優先順）:

1. **`complete_task` のコメント必須化** — 担当者による検証結果コメントが存在しないと `in_review` に進めない。「検証結果を書け」という散文ルールをサーバー側バリデーションに昇格させる
2. **`claim_task` / `complete_task` の RoleGuard 昇格** — 現在「運用で制御」になっている worker 専用操作を実装ブロックにする
3. **1 セッション 1 プロジェクト 1 ロールの制限** — 現在は同一セッションが manager + worker + reviewer を兼任でき、レビューゲートを自作自演で素通りできる
4. **`complete_story` の整合チェック** — 配下 Task が全て `accepted` / `canceled` でなければ完了できないようにする

対象プロジェクト側でやれること:

- lint / CI に落とす: 1 ファイル行数上限（max-lines）、レイヤ依存方向の強制（eslint-plugin-boundaries 等）、重複リテラル検出、未使用エクスポート検出
- 「知識として配る」のではなく「設定ファイルとして配る」— wacha が lint プリセットや CI テンプレートを配布する形にすれば、規範がモデルの解釈を経由せずに効く

### 構造 2: 判断密度でモデルを配置する

wacha の role 構造は判断の濃淡と一致している。

- **判断が濃い**: manager（分解・受入）、reviewer（差分の妥当性判定）
- **判断が薄い**: worker（完了条件が良く書けた Task の実行）

したがって:

- **強いモデルは manager / reviewer に割り当てる。** 分解とレビューは実装よりトークン消費がはるかに少ないので、強いモデルを常用できなくても、この 2 役だけなら経済的に成立しやすい
- **弱いモデルは worker に割り当てる。** 出力は必ず強いモデルのレビューゲートを通るので、誤りは構造で捕まる
- **タスク分解の質（強いモデルの仕事）は、worker に渡すドキュメントの質より効く。** 完了条件が曖昧な Task を弱いモデルに渡すのが最悪の組み合わせであり、逆に Given/When/Then が具体的なら弱いモデルでも判断量が少なくて済む

「弱いモデルを賢くする」のではなく「弱いモデルの誤りを構造で捕まえる」。これがこの配置の原理である。

ただしこの配置は、構造 1 の 2〜3（RoleGuard 昇格・兼任制限）が実装されて初めて機械的に保証される。現状はレビューゲート自体が運用依存なので、先に wacha 本体のゲートを固めることが前提になる。

## 運用ループ

改善が一方向で終わらないための仕組みは実装済み:

- `propose-knowledge-update`（全ロール）で提案を出す
- `apply-knowledge-update`（manager）で採否判断・反映
- `knowledge/CHANGELOG.md` に採用も見送りも記録し、重複提案を防ぐ

この文書自体への追記も同じ扱いでよい。モデル運用で新しい傾向（新モデルの得手不得手、新しい再発パターン）が観測されたら、根拠となるセッションや task への参照付きでここに足す。

## まとめ

| 手段 | 効果 | 限界 |
| --- | --- | --- |
| Knowledge / Skill（散文） | 床を上げ、分散を縮める | 解釈がモデルに律速される。増やすほど薄まる |
| 機械的ゲート（lint / CI / サーバー側検証） | 解釈を経由しないのでモデル非依存 | 機械化できる違反にしか効かない |
| 判断密度でのモデル配置 | 強いモデルの費用を判断の濃い所に集中できる | ゲートが機械化されていることが前提 |
